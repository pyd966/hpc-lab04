# ABE Phase 30: Ricci 逐行分块优化报告

日期：2026-08-25

## 1. 结论

本阶段保留了 RHS 中六个 Ricci 更新的 `j=1` 行分块实现。受控的六轮
ABBAAB 对照中：

| 版本 | 运行次数 | Evolve 均值 | 最小值 | 最大值 |
|---|---:|---:|---:|---:|
| 原始六次整数组遍历 | 3 | 28.9043 s | 28.8323 s | 29.0204 s |
| 逐行分块 | 3 | 26.8057 s | 26.6089 s | 26.9687 s |

逐行分块使 `t=0..4` 的 Evolve 时间下降 **7.26%**，即加速 1.078 倍。
三组输出逐位一致，六轮课程检查全部 PASS。按演化长度线性粗略外推，
`Evolve(40)` 可少约 21 秒；正式 `t=40` 仍应单独计时，短程外推不是最终成绩。

这次收益不是来自增加 OpenMP 线程，也不是来自少算公式。主要原因是六个 Ricci
分量在同一条 `j` 行上重复使用的大量输入能够留在近端缓存中。指令总数基本不变，
但 IPC 从 1.43 稳定提高到 1.55。

## 2. 优化前为什么慢

优化前的 `compute_rhs_bssn_` 占 51.05% 的 cycles。六个 Ricci 大表达式分别
占用：

| 分量所在原代码行 | cycles self |
|---|---:|
| `bssn_rhs.f90:828` | 4.09% |
| `bssn_rhs.f90:750` | 3.63% |
| `bssn_rhs.f90:789` | 3.21% |
| `bssn_rhs.f90:655` | 2.91% |
| `bssn_rhs.f90:711` | 1.74% |
| `bssn_rhs.f90:683` | 1.18% |
| 合计 | **16.76%** |

原写法是六个完整的 Fortran 数组表达式。编译器已经能够沿连续的第一维 `i`
生成 128-bit NEON 双精度 SIMD，所以问题不是“完全没有向量化”。问题在遍历顺序：

```text
完整 Rxx 三维数组 -> 完整 Ryy 三维数组 -> ... -> 完整 Ryz 三维数组
```

六个分量会重复读取逆度规、连接系数和度规导数。完成一个三维分量再进入下一个
分量时，前面读过的输入通常已经离开 L1/L2，因而相同数据要再次从更远的缓存层次
取回。

## 3. 实现方式

新路径位于 `src/bssn_ricci_tiled.inc`，遍历次序是：

```text
k -> 一个 j 行 -> Rxx/Ryy/Rzz/Rxy/Rxz/Ryz -> SIMD i
```

具体约束如下：

1. 六个分量仍是六个独立的紧凑 SIMD 循环，没有合成一个寄存器压力很大的
   单点超大循环；
2. 最内层始终是 Fortran 连续存储的 `i` 维；
3. `j=1` 表示完成一行的六个分量后才前进到下一行，使共同输入的复用距离最短；
4. 每个点的表达式、括号和运算顺序不变，只改变独立点和独立输出之间的执行顺序；
5. CMake 保留开关 `AMSS_ENABLE_RHS_RICCI_TILING`，生产默认开启，
   `AMSS_RHS_RICCI_TILE_J=1`。

静态检查将六个新表达式去掉数组下标和空白后与原表达式逐字符比较，六项全部
一致。GFortran 的 vectorization report 显示六个最内层循环都使用 16-byte
向量。接受版 RHS 符号大小为 `0x198ec` 字节，略小于原版 `0x199ec`；栈帧仍为
`0x5e0`，没有增加栈帧或出现“把六个分量同时放入寄存器”造成的明显 spill 信号。

## 4. Tile sweep 和失败候选

探索作业为 `165006`，工件目录是
`profile/abe-rhs-ricci-tile-20260825T170315Z-14`。运行顺序为
`off, j1, j2, j4, j8, off`：

| 候选 | Evolve | IPC | L1D miss | 平均 CPU* |
|---|---:|---:|---:|---:|
| OFF（开头） | 29.8291 s | 1.44 | 4.15% | 23.920 |
| `j=1` | 26.5594 s | 1.54 | 3.97% | 23.842 |
| `j=2` | 28.4442 s | 1.56 | 4.05% | 23.290 |
| `j=4` | 29.0568 s | 1.55 | 4.10% | 21.898 |
| `j=8` | 31.0405 s | 1.57 | 4.23% | 21.209 |
| OFF（结尾） | 33.6592 s | 1.44 | 4.12% | 21.382 |

`*` 这里的平均 CPU 覆盖初始化和 Evolve 全窗口，不能单独代表 RHS 并行度。

这组作业后半段发生明显的节点速度漂移，因此没有用首尾 OFF 的均值直接宣称收益。
但 tile 大小呈现了有意义的趋势：`j=1` 最好，`j=2/4` 逐渐失去优势，`j=8`
回退。一个 `j` 行所需的共同输入更容易留在 L1；tile 变大后工作集迅速扩大，
分量间的复用距离也变长，最终抵消分块收益。

针对 `j=1` 又提交了独立验证作业 `165051`，工件目录为
`profile/abe-rhs-ricci-tile-20260825T171112Z-14`，顺序为
`OFF, j1, j1, OFF, OFF, j1`。三组结果为：

| 序号 | OFF | `j=1` | `j=1` 相对下降 |
|---:|---:|---:|---:|
| 1 | 28.8323 s | 26.6089 s | 7.71% |
| 2 | 28.8601 s | 26.9687 s | 6.55% |
| 3 | 29.0204 s | 26.8396 s | 7.51% |

三对都同方向，波动区间不重叠，因此采用 `j=1`，拒绝 `j=2/4/8`。

## 5. 接受后的完整 profile

接受后 profile 作业是 `165092`，工件目录为
`profile/abe-20260825T171942Z-14`。`perf stat` 的 Evolve 为 26.4063 秒，
`perf record` 的 Evolve 为 26.2435 秒，共采到 66,219 个样本且无丢样。

### 5.1 硬件计数器

| 指标 | 优化前 | 接受后 | 解释 |
|---|---:|---:|---|
| IPC | 1.41 | 1.54 | 同样数量的指令用更少周期完成 |
| cycles | 2.109e12 | 1.938e12 | 下降 8.11% |
| instructions | 2.974e12 | 2.978e12 | 增加 0.14%，基本不变 |
| L1D miss rate | 4.17% | 3.99% | 改善 |
| L1D misses | 45.45e9 | 43.68e9 | 下降 3.89% |
| LLC miss rate | 49.31% | 48.28% | 改善 |
| LLC load misses | 29.28e9 | 24.63e9 | 下降 15.88% |
| branch miss rate | 0.47% | 0.49% | 轻微变差，不是瓶颈 |
| dTLB miss rate | 1.43% | 1.50% | 轻微变差，收益并非来自 TLB |

这里优化前后是两个独立 profile 作业，硬件计数器用于解释机制；最终收益以第 4 节
的交错 A/B 为准。

### 5.2 热点变化

| 函数 | 优化前 | 接受后 |
|---|---:|---:|
| `compute_rhs_bssn_` | 51.05% | 46.74% |
| `__memcpy_sve` | 9.68% | 10.73% |
| `lopsided_core_` | 8.83% | 9.61% |
| `__memset_sve_zva64` | 5.37% | 5.69% |
| `fdderivs_` | 4.63% | 4.71% |
| `kodis_` | 2.46% | 2.84% |
| `prolong3_pair_kernel_` | 2.52% | 2.69% |
| `fderivs_` | 2.54% | 2.63% |
| `rungekutta4_rout_` | 1.94% | 2.34% |

其余函数的百分比上升主要是分母变小，不代表它们变慢。六个 Ricci 更新在新行号
`30/57/84/122/160/198` 上合计为 **9.55%**，相比原来的 16.76% 明显下降。
用“采样占比乘本次 record 墙钟”作粗略估计，六个 Ricci 更新约快 49%，整个 RHS
约快 19%；这只是采样估计，不替代受控计时。

### 5.3 OpenMP 状态

本阶段没有修改 OpenMP 调度、线程数或绑核。仍是单进程、30 个 OpenMP worker、
`OMP_PLACES=cores`、`OMP_PROC_BIND=close`，静态层 24、移动层 30。

接受后诊断中 level 5--8 的 block phase utilization 分别为 84.0%、88.3%、
86.1%、89.1%。level 1--4 约为 79%--80%。level 0 只有 9 个可分 block，利用率
约 30%，这是粗层任务数量的上限。此次优化提高的是每个 block 内 Ricci 内核的
单核效率，不会改变 level 0 的并行几何。

## 6. 正确性和保留内容

- 探索与验证共 12 次运行，课程检查全部 PASS；
- 每个候选的四个主要输出文件去掉时间戳头后均与 OFF 逐位一致；
- 接受后的 `perf stat` 与 `perf record` 两次输出也逐位一致；
- 默认仍为严格 `-O3`，没有启用 `-Ofast` 或 fast-math；
- 生产保留逐行实现、CMake 开关、多 tile sweep 和 ABBAAB 验证脚本，便于复现。

## 7. 对后续计划的影响

P6 的 Ricci 分块达到了原计划 3%--7% 区间的上沿，且没有牺牲 SIMD 或增加栈帧。
当前 profile 的重心已经向数据搬运移动：`memcpy + memset` 合计 16.42%，
`lopsided_core_` 为 9.61%。RHS 仍是第一热点，但继续改动应针对新的具体热行
`bssn_rhs.f90:545/489`，不能再泛化地合并大表达式。

原计划中当前环境可执行的尾部实验已经基本闭环：lopsided/导数 batch、RHS 多种
融合、huge page、对齐、LTO、SVE 和热点文件架构参数均已做过 A/B，只有本轮
Ricci 逐行分块得到显著新收益。P7 的 RHS/RK4 融合需要改变 RHS 的生命周期，
风险高且 RK 自身目前仅占 2.34%，暂不保留原型。P4 的 60 物理核几何必须等到
真正提供 60 个物理核的评测分配后再做；当前 60 个逻辑 CPU 只对应 30 个物理核，
不能用 SMT sibling 冒充评测拓扑。

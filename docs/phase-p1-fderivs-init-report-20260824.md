# P1 阶段报告：fderivs 临时数组清零评估

日期：2026-08-24

## 结论

本阶段评估了 `fderivs` 中整数组清零是否可以改成只初始化未覆盖区域。两个候选实现都保持了数值结果逐位一致，但端到端性能稳定变差，因此没有合入生产路径。最终代码仍使用原来的整数组清零和已有 `fderivs` SIMD 内部循环。

结论不是“内存清零没有成本”，而是当前 AArch64 C 库的 `memset` 已经用专门的 ZVA 写零指令实现。手写边界循环虽然少写了一些字节，却引入了更多 Fortran 循环、边界判断和标量存储，整体更慢。

## 1. 代码语义与可优化边界

`src/diff_new.f90` 中的 `fderivs` 接收三个 `intent(out)` 输出数组 `fx/fy/fz`。当前启用的 BAM-comparison 路径分为两块：

1. 距离每个方向边界至少两个点的内部盒使用四阶中心差分，最内层 i 循环带有 `!$omp simd`。
2. 其余满足正负一个 ghost 点条件的点使用二阶中心差分；更外层的点保持零值。

因此，原来的 `fx=0; fy=0; fz=0` 并不是可随意删除的冗余操作。它覆盖了二阶差分也不能计算的边界点，以及 SIMD 代码原本没有遍历的最后一层。删除后必须显式写回这些点，否则 `intent(out)` 数组会包含未定义值。

本阶段只研究 `fderivs`，没有修改 `fdderivs`、RHS、OpenMP 调度或编译参数。

## 2. 候选一：完整网格扫描中局部写零

实现方式：去掉三个整数组清零，在原有 shell 循环中遍历到 `ex(1:3)` 的最后一个索引；对不属于四阶内部盒的点先写三个零，再对满足二阶条件的点覆盖为差分结果。

这样保证了输出覆盖完整，但循环仍然扫描整个网格，并且每个 shell 点都执行内部盒判断。该候选通过了 Fortran 语法检查、课程检查和输出逐位比较。

同一作业内交错运行结果：

| 作业 | full（原清零） | partial（局部写零） | 变化 |
|---|---:|---:|---:|
| 156332 | 29.8212 s | 30.3871 s | +1.90% |
| 156385 | 30.0793 s | 31.2896 s | +4.02% |
| 两次均值 | 29.9503 s | 30.8384 s | +2.97% |

两次 partial 运行的课程检查均为 PASS，`bssn_ADMQs.dat`、`bssn_BH.dat`、`bssn_constraint.dat`、`bssn_psi4.dat` 相对同作业内 full 运行逐位一致。硬件计数器也解释了负收益：partial 的 IPC 约为 1.455，而 full 约为 1.485；branch miss 从约 0.43% 升到约 0.52%。L1D/LLC miss 没有出现足以抵消控制流开销的下降。

## 3. 候选二：有效盒加六个外部 slab

第二个候选先计算二阶差分有效盒：

`[max(1, imin+1), min(ex(1), imax-1)] × [max(1, jmin+1), min(ex(2), jmax-1)] × [max(1, kmin+1), min(ex(3), kmax-1)]`

有效盒内只处理四阶内部盒之外的二阶 shell；有效盒外用六个互不重叠的 x/y/z slab 写零，避免对整个数组做条件扫描。有效盒为空时退化为完整写零。这个版本同样逐位一致，课程检查全部 PASS。

四轮同一作业交错结果（`full → slab → slab → full`）：

| 版本 | 运行 1 | 运行 2 | 均值 | 平均 CPU |
|---|---:|---:|---:|---:|
| full | 29.7446 s | 29.6172 s | 29.6809 s | 22.332 |
| slab | 30.1811 s | 30.3548 s | 30.2680 s | 22.319 |

slab 比 full 慢 0.5871 秒，即 1.98%。其 IPC 为约 1.47，对 full 的 1.50 更低；branch miss 约 0.59%，高于 full 的约 0.43%。平均 CPU 几乎没有差别，说明不是 OpenMP 线程数或绑核变化造成的差异，而是函数内部循环和存储方式本身更差。

单独的一轮 A/B（作业 156556）也得到 `full=29.7454 s`、`slab=30.4428 s`，方向一致。

## 4. 最终生产 profile

实验候选撤销后，在生产基线上重新执行了带 `-g -O3 -fno-omit-frame-pointer` 的 perf stat/record profile：

工件目录：`profile/abe-20260824T131707Z-14/`

- `perf stat` pass：Evolve 28.9787 s，墙钟 31.9716 s。
- `perf record` pass：Evolve 29.3071 s，墙钟 32.0297 s。
- record 样本约 74K，丢样本 0。
- 平均 CPU 利用约 24.09 个逻辑 CPU（30 个 OpenMP 线程的整体运行平均值）。
- OpenMP 绑定仍为 `OMP_PLACES=cores`、`OMP_PROC_BIND=close`；细网格 level 5--8 的实际 block 数为 30。

### 4.1 热点

| 函数/库调用 | cycles 样本占比 | 可定位位置 |
|---|---:|---|
| `compute_rhs_bssn_` | 41.28% | `src/bssn_rhs.f90:345, 514, 609, 648, 687` 等数组循环 |
| `__memcpy_sve` | 12.86% | `memcpy_sve.S`，由块/变量同步和数组搬运触发 |
| `lopsided_` | 8.71% | `src/lopsidediff.f90:100, 277, 302, 330, 355` |
| `__memset_sve_zva64` | 6.02% | 多个 Fortran 输出初始化和临时数组清零 |
| `prolong3_` | 4.76% | `src/prolongrestrict_cell.f90:2136, 2143` |
| `fdderivs_` | 4.61% | `src/diff_new.f90:550, 556` 等二阶导数 stencil |
| `fderivs_` | 2.46% | `src/diff_new.f90:95` 四阶内部 stencil |

`fderivs` 已经不是主要热点；即使完全消除其清零时间，端到端上限也受 2.46% 函数占比限制。本阶段 A/B 实际表明，尝试替换清零反而损失约 2--3%。

### 4.2 微架构与并行现象

- IPC 约 1.79，说明执行并不接近每周期完成多条指令的计算上限。
- L1D load miss 3.83%，LLC load miss 37.30%，dTLB miss 3.43%。LLC miss 偏高，和大量数组搬运、stencil 的多数组访问相符；这更像访存压力，而不是算术单元饱和。
- branch miss 0.62%，绝对值不高；slab/partial 的升高反而说明增加控制流会直接伤害性能。
- i-cache miss 0.06%、iTLB miss 约 0.00%，指令取指不是瓶颈。
- 当前程序没有 MPI 通信；OpenMP 诊断显示粗网格 block 数少、细网格 block 数为 30。因此整体平均 CPU 低于 30，主要来自粗网格、串行阶段和不同 level 的工作量，而不是绑核失效。

## 5. 阶段决定与后续方向

本阶段不保留任何生产代码改动。原始整数组清零继续保留，因为它由 AArch64 libc 的高效 `memset` 执行；未来如果改变数据布局或能在上游保证所有输出点都被无条件写入，才值得重新评估。

后续优化优先级建议如下：

1. `compute_rhs_bssn_`：占 41.28%，应继续检查数组临时量、重复加载、循环融合和可验证的 SIMD；这是目前最大的收益来源。
2. `memcpy`：占 12.86%，应沿块/变量同步调用路径确认哪些搬运是必要的，优先减少中间缓冲和重复拷贝，而不是替换 libc memcpy。
3. `lopsided_` 与 `fdderivs_`：合计约 13.3%，继续从内存访问顺序、导数批量计算和已有 SIMD 的实际生成代码入手。
4. `prolong3_`/`restrict3_`：约束在 AMR 插值/限制阶段的数组搬运和细粒度任务并行；需要结合 level/block 任务统计，不宜只增加线程。
5. `memset`：目前不应单独手写替代；只有和更大的 RHS/导数融合一起研究时，才可能通过“计算时直接覆盖输出”真正减少写流量。

下一阶段应以 `compute_rhs_bssn_` 和相关 `memcpy` 调用路径为主，并继续使用同作业交错 A/B、逐位输出比较和带符号 profile，避免把硬件频率或调度波动误判为优化收益。
